# #290 implementation and validation report

## Scope and authority

24 logical corpora are declared in [corpus-authority.json](corpus-authority.json):
23 vector corpora plus the Rust example fixture. The docs tree contains 61 IDs,
the package tree 148; the only shared IDs are the eight Profile-C cases. The
prompt's 50 docs IDs omits canonicalization's 11. Live inventories including IDs
are available through `pnpm verify:corpus-authority --json`.

The [authority decision and consumer map](corpus-authority.md) were written before
projection implementation. Profile-C's docs file is authoritative because its
normative profile designates it, Go/Python independently consume it, and it
contains committed Encoding B artifacts/keys. The package secondary permits
standalone release packaging without bundling or mirroring the docs tree.

Only Profile-C is projected. Authorization, delegation and SignedKRL corpora
remain distinct. Trusted-time's package file is an official source named by the
conformance spec; its engine/runtime coverage remains TypeScript-only.

## Projection and consumer change

`expected.outcome` maps to the identical `expected.status` value (`ok`,
`state-hash-mismatch`, `compute-error`). Each mode's optional reason is explicitly
listed in the authority document. Unsupported modes, outcomes, expected fields,
layouts and strategies fail rather than being silently interpreted.

The generated JSON retains source metadata, IDs/order, inputs, strategies,
signed artifacts, public keys and verification time. Recursive key ordering,
two-space indentation and final LF define generated bytes. Source corpus version
1.1.0 is preserved, replacing the old independently maintained secondary version
1.0.0; this is corpus metadata, not a protocol/wire-format change.

The TypeScript conformance runner now consumes committed Encoding B fixtures,
including key algorithm, rather than minting replacement artifacts. Three
additional assertions compare recomputed committed hashes to the signed
`auth.state_hash`, bringing package conformance from 259 to 262 assertions.
The original secondary IDs, inputs, modes, strategies, statuses and reasons were
compared against HEAD and all preserved. Description/metadata now come from the
authority. No docs vector or normative specification was edited.

No build or prepack copies/generates vector trees. The explicit maintainer write
command `pnpm project:profile-c` writes only the secondary Profile-C file. CI's
`pnpm verify:corpus-authority && pnpm test:corpus-authority` is read-only and is
added to the existing spec-claims job. Both complete structural validation and
byte-exact equality are required; a source-shaped in-memory comparison verifies
no information was lost. This comparison never writes back to the authority.

## Runtime limitations and pre-existing mismatch

The optional Go package driver was not executed as an independent verifier: it
requires an adapter, and its bundled Python adapter fails before handling
requests (#306). Driver/source presence and frozen lookup operations are not
cross-language evidence. Root Go/Python success applies only to their three
actual corpora. Rust success applies only to its bundled auth/key fixture.

The manual `gateway.vectors.test.ts` is absent from the default guard test list.
It was explicitly executed to avoid counting file presence as passing evidence:

- canonicalization: PASS;
- authorization `auth-allow-valid`: FAIL, `DENY/INVALID_SIGNATURE` rather than
  `ALLOW`;
- PEP `pep-allow-upstream-success`: FAIL, HTTP 403 rather than 200.

`git diff --quiet HEAD -- packages/core packages/guard
 docs/spec/test-vectors/authorization-v1.json
 docs/spec/test-vectors/pep-vectors-v1.json` returned zero: those consumer sources
and fixtures are unchanged by #290. This is an existing consumer/corpus mismatch,
not a Profile-C projection divergence. The standalone authorization/PEP harnesses
pass, but that does not make the manual Core/gateway consumer pass. The manifest
marks these failing consumers blocked. No signatures, protocol behavior or
expected results were altered to hide the mismatch.

## Spec claims and CANON-ESC-001

PROFILE-C-001 continues to cite docs `profile-c-002` through the Python runner and
its separate guard integration test. Its levels and obligations are unchanged.
A forbidden inference now explicitly rejects projection equality → independent
corpus evidence. Generated output is not added as a second evidence corpus.
All other existing vector evidence references were inspected: authorization,
delegation and SignedKRL references retain their distinct paths and IDs.

CANON-ESC-001 remains unresolved/deferred with maintainer decision required. No
repository definition was inferred for this placeholder. Current Profile-C
state and signing-payload strings are plain printable ASCII without disputed
escaping; PEM formatting lies outside signing payloads. Projection preserves
parsed values and committed signature bytes and does not implement signing
canonicalization. A test pins this scope observation. #290's current projection
can be evaluated independently; escape-sensitive future vectors need separate
lock review. Neither this test nor structural PASS resolves CANON-ESC-001.
