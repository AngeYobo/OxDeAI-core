# Corpus authority and consumer topology (#290)

## Profile-C authority decision (before projection implementation)

The sole authority for the shared logical Profile-C corpus is
`docs/spec/test-vectors/profile-c-state-verification.json`.
`packages/conformance/vectors/profile-c-state-verification.json` is its generated
package representation, never a second editable authority.

Rationale: the normative external-provider profile §2.3.4 explicitly references
the docs corpus; root Go and Python independently consume its eight modes,
including committed Encoding B signed artifacts and public keys. Package release
packaging includes `vectors`, not `docs/spec`, so a committed one-way projection
preserves standalone package use. Authority follows normative ownership and
consumer architecture, not ease of transformation. The TypeScript consumer must
use the preserved artifacts, keys and verification time rather than synthesize
replacement signatures. No entire-tree copying or prepack generation is permitted.

Initial inspection: the docs tree has 61 IDs across six files (the task's 50
omits the 11 canonicalization cases), and the package tree has 148 IDs across
18 files. Exactly eight IDs overlap, all Profile-C. Authorization, delegation
and SignedKRL corpora with different IDs remain distinct. Expected-result
similarity does not establish corpus identity.

## Projection contract

All source metadata and vector fields are preserved, including IDs, modes,
state inputs, strategies, descriptions, auth, opts and the source version.
Only `expected.outcome` is represented as `expected.status`. The optional
`expected.reason` is a deterministic diagnostic derived from the mode; it is not
a protocol violation code or an independently authored expected result. The old
TypeScript consumer asserted status, not these reason strings.

| Source outcome | Projected status | Reason |
|---|---|---|
| `ok` | `ok` | Absent |
| `state-hash-mismatch` | `state-hash-mismatch` | Mode-specific diagnostic defined in the projection mapping |
| `compute-error` | `compute-error` | `computeStateHash threw; execution blocked fail-closed` |

Projection rejects unknown modes, unexpected outcomes, unknown expected-result
fields, duplicate IDs and unsupported field layouts. JSON keys sort recursively,
vector order remains authoritative, serialization uses two spaces plus final LF.
The projection does not canonicalize signing payloads or re-sign artifacts.
Source descriptions predate this authority decision and are preserved verbatim;
representation ownership comes from the manifest, not those descriptive links.
Semantic verification reconstructs source-shaped data in memory and compares all
fields; this is a validation check, not a reverse write/synchronization command.
CI also requires exact serialized generated bytes.

## CANON-ESC-001 boundary

CANON-ESC-001 remains unresolved/deferred. It has no independently defined
repository contract to resolve here. Current Profile-C state and signed-payload
strings use plain printable ASCII without disputed escape characters; PEM
newlines are key-container formatting, outside the signing payload. Projection
preserves those values and signature bytes; JSON file pretty-printing is not
canonical signing serialization. Thus #290 can establish authority and projection
for the current eight cases without deciding an escaping rule. New corpus inputs
needing such a rule must be reviewed against the unresolved lock; this work does
not certify general escaping or whole-protocol cross-language parity.

The trusted-time package file is explicitly designated an official source by
`docs/spec/conformance/conformance-v1.md` §4 and is classified normative; its
TypeScript-only consumers do not imply portable engine support in other runtimes.

## Authority manifest and CI

[corpus-authority.json](corpus-authority.json) declares 24 logical corpora: 23
vector corpora across the two trees plus the Rust example fixture corpus. Each
has one authority path, one or more representations, status, semantic scope,
governing specification reference and concrete consumer bindings. Other than
Profile-C, a representation belongs to exactly one corpus with no mirroring.
Rust's keyset is supporting fixture material, not another representation.

`pnpm verify:corpus-authority` validates unique authority/representation ownership,
all vector files registered, per-file unique IDs, consumers' source-file bindings,
and exact Profile-C projection. `--json` emits derived IDs for the S_freeze
bundle. `pnpm test:corpus-authority` exercises drift/unsupported mappings.
Both run in the existing `spec-claims` CI job before spec-claim verification.
CI never writes output. `pnpm project:profile-c` is the explicit one-way maintainer
write command and writes only the secondary Profile-C file.

Metadata is curated traceability: file/binding presence does not prove consumer
logic or execution. Actual execution results are recorded separately in
[corpus-authority-validation.md](corpus-authority-validation.md). No code-level
proof or whole-protocol conformance is inferred from structural PASS.

The generic package Go driver is manual/adapter-dependent, not the root Go
validator. Its Python adapter fails at import with `KeyError: intent_id` (#306);
several later operations also use frozen expected-result lookup. It is marked
blocked, not independent runtime coverage. Rust's four tests use one local auth
fixture plus keyset, never a vector tree. `gateway.vectors.test.ts` now runs in
the default guard test list alongside gateway enforcement and authority tests.
Its PEP coverage is a seven-case subset of the common A/B gateway surface; two
snapshot-dependent cases have an explicit deferred profile/surface disposition.
Authorization fixture-context checks do not establish live-state verification. See [gateway parity validation](gateway-vector-parity-validation.md)
for the pre-existing failure diagnosis and the scoped repair.

The legacy conformance extractor reads and rewrites selected package baselines;
those maintenance reads are recorded below, not counted as verifier evidence.
It does not write Profile-C. Generators/extractors are not invoked by #290.

are explanatory annotations, not separately executable protocol reason codes.
