# OxDeAI 2.0 Residual Security Scope

**Status:** Draft — release-boundary document for the OxDeAI 2.0 line.
**Companion to:** `docs/audits/openzeppelin-scope-v2.md` (review scope), `docs/audits/protocol-audit-post-interoperability.md` (prior internal audit, 2026-06-04), `docs/architecture/decisions/tier1-evaluator-input-provenance.md` (ADR governing §3), `docs/spec/state-provider-requirements.md` (normative spec governing §3).

---

## 1. Purpose

This is a **release-boundary document**, not a backlog dump. Its purpose is to state, precisely and in one place, which security guarantees OxDeAI 2.0 targets and which architectural boundaries remain outside those guarantees **even if the OpenZeppelin review in `openzeppelin-scope-v2.md` passes with no findings**. A residual listed here is not necessarily a defect — several are explicit, documented design boundaries (e.g., "signed does not mean authoritative," §8). What makes this document necessary is that the public claims made for the 2.0 release must not exceed what is listed here as targeted (§2), and must explicitly carry the caveats listed for each residual.

This document does not track ordinary engineering backlog. Open issues are referenced here only where they bound a security property this release does, or could be perceived to, claim.

---

## 2. Guarantees targeted by 2.0

OxDeAI 2.0 targets, narrowly:

- **Deterministic pre-execution authorization** — `(intent, state, policy, evaluationTime) → ALLOW | DENY`, implemented in `packages/core/src/policy/PolicyEngine.ts`, with no ambient randomness or shared mutable state in the pure decision path.
- **Fail-closed reviewed enforcement path** — `OxDeAIGuard`/`createSecureGuard` in `packages/guard/src/`, where every rejection (DENY, missing/invalid authorization, provenance conflict, replay, CAS conflict) blocks execution before the protected callback runs.
- **Cryptographic binding of authorization artifacts** — Ed25519 signing and verification, canonical encoding, domain-separated signing payloads, for `AuthorizationV1` and `DelegationV1`.
- **Trusted execution-context reconciliation** — on the `createSecureGuard` path only: proposer-declared `agent_id`, `depth`, and `tool` (when a trusted route premise for `tool` exists) cannot override a trusted premise supplied via `createTrustedExecutionContext`; a conflict fails closed with `OxDeAIProvenanceConflictError` before evaluation.
- **Audience/replay/freshness controls** — required `expectedAudience` binding, single-use `auth_id`/`delegation_id` consumption via a pluggable `ReplayStore`, and trusted-evaluation-time-based freshness bounds (`maxClockSkewSeconds`, `maxIntentAgeSeconds`).
- **Versioned policy-state conflict detection where configured** — `getState()`/`setState(nextState, expectedVersion)` compare-and-set semantics, detecting (not preventing) a concurrent state mutation between read and commit.

Every residual below narrows one of these six targeted guarantees. None of the residuals below are claimed as solved by 2.0.

## 3. Residual: evaluator/state authority (#197)

`createSecureGuard` protects **reconciliation of trusted execution context** — it ensures a proposer's self-declared `agent_id`, `depth`, or `tool` claim cannot silently override a premise the PEP supplied after authenticating the caller. This is real and tested (`packages/guard/src/test/guard.provenance.test.ts`).

It does **not** make arbitrary deployment-provided state authoritative. `getState()` remains, exactly as before, a function the deployment supplies; the guard's only check against it is `computeStateHash(liveState) === authorization.state_hash` (hash consistency) plus CAS version-conflict detection at `setState()`. Neither check proves the state source is honest, current, or non-compromised. `docs/spec/state-provider-requirements.md §1.2` states this directly: *"A compromised or non-compliant state provider can return a manufactured state object whose hash matches a valid authorization... The protocol cannot detect this at the PEP layer."*

State-source authority remains a deployment responsibility, satisfiable by following `docs/spec/state-provider-requirements.md`, but not enforced or verified by the protocol itself.

**Therefore: complete Tier 1 evaluator-input provenance is not claimed for 2.0.** The provenance guarantee 2.0 does claim is scoped exactly to the fields `reconcileWithTrustedContext` actually reconciles (`agent_id`, `tool`, `depth`, plus conflict-only checks on `principal_id`, `tenant_id`, `adapter_id`, `route_classification`) — not to state or policy authority. [#197](https://github.com/oxdeai/oxdeai/issues/197) remains open and tracks exactly this remaining half.

## 4. Residual: external-resource TOCTOU (#253)

The guard's CAS/state-version check protects the boundary of OxDeAI's own policy-state transition: if a concurrent evaluator advances the state version between `getState()` and `setState()`, the later `setState()` call returns `false` and `OxDeAIConflictError` blocks execution.

This does **not** automatically serialize mutation of an **external** resource that the protected `execute()` callback goes on to touch. [#253](https://github.com/oxdeai/oxdeai/issues/253) states the gap precisely: *"A signed authorization or state hash proves what premises were evaluated. It does not guarantee that those premises are still current when the external mutation occurs."* An authorization can be issued against resource version `v12`, the resource can change to `v13` before `execute()` runs, and OxDeAI's own state CAS can succeed regardless — because it is checking OxDeAI's policy state, not the external resource's version.

True resource-side TOCTOU protection requires the resource itself to expose, and the executor to use, an atomic precondition mechanism — an HTTP `If-Match` header, a database row version check, a transactional conditional write, or equivalent. OxDeAI does not currently provide or require such a mechanism for arbitrary external resources.

**Do not claim generic TOCTOU safety for 2.0.** The TOCTOU protection that does exist and is conformance-tested (`profile-c-005 / toctou-stale-state` in `packages/conformance/vectors/profile-c-state-verification.json`) is scoped to OxDeAI's own internal policy state, not to arbitrary external side effects. [#253](https://github.com/oxdeai/oxdeai/issues/253) is open and design-only as of this document.

## 5. Residual: post-execution-start audit semantics (#238)

`onDecision` and `onBoundaryEvent` are disjoint, by construction (`packages/guard/src/types.ts`, `packages/guard/src/boundaryEvent.ts`):

```text
valid DENY                              → onDecision only      (decision record emitted)
guard rejection before execute() starts → onBoundaryEvent only (no decision record)
```

Everything up through a successful `ALLOW` — evaluation, authorization verification, replay consumption, hash binding, and the CAS state commit — is captured on one of these two streams before the protected `execute()` callback is ever invoked.

The gap, as [#238](https://github.com/oxdeai/oxdeai/issues/238) describes it: once `execute()` has actually started, a failure inside it (the callback throwing) is **not** a policy `DENY` and must not be represented as one, but the current lifecycle also produces no `onBoundaryEvent` for it, since boundary events are specifically for pre-execution rejections. A protected callback that throws after execution has legitimately started can currently leave that specific request with no final decision record on either stream.

**Do not claim that every post-execution-start failure is currently captured by audit events.** What 2.0 does guarantee is that nothing before `execute()` starts is unaccounted for on one of the two streams. [#238](https://github.com/oxdeai/oxdeai/issues/238) is open and design-only as of this document; its own acceptance criteria explicitly state the eventual fix must not claim that external side effects were rolled back unless a specific adapter/execution mechanism provides that guarantee.

## 6. Residual: human approval / STEP_UP (#245)

No human-approval or step-up-authorization workflow exists in the shipped `PolicyEngine` or guard as of 2.0. [#245](https://github.com/oxdeai/oxdeai/issues/245) is a design-only issue, explicitly gated with "do not implement yet" in its own body, pending resolution of how an approval binds to a specific action when a secure resubmission necessarily carries a fresh nonce and timestamp (and therefore a different request hash than what was originally reviewed).

This is **not part of 2.0 authorization semantics** and must not be described as such in any 2.0 release material.

If and when it is implemented, the required invariant (already stated in the issue, not yet built) is: a fresh resubmission representing the *same* action MAY be allowed to inherit an approval after full re-evaluation, but a request representing a materially different action MUST NOT inherit an approval granted for a different one, and an approval MUST NOT create replay/freshness exceptions for the originally-reviewed request. Approval binding will require a separately specified normalized-action-snapshot concept and compatibility semantics that do not exist today.

## 7. Residual: adapter provenance

None of the five shipped framework adapters (`@oxdeai/langgraph`, `@oxdeai/crewai`, `@oxdeai/autogen`, `@oxdeai/openai-agents`, `@oxdeai/openclaw`) construct a `TrustedExecutionContext` or call `createSecureGuard`. All five delegate to the lower-level `OxDeAIGuard` entry point. This is documented, current, per-adapter posture — see e.g. `packages/langgraph/README.md`'s "Trust profile" section, added as part of the 2.0 pre-freeze work:

> "Declared. This adapter integrates the lower-level `OxDeAIGuard` boundary. `agent_id` is fixed by deployment configuration (`config.agentId`) and is not proposer-controlled... Tool identity and recursion depth are not established from a `TrustedExecutionContext` on this path."

Concretely, for every current adapter:

- Framework tool-call inputs (name, args) are declared by the calling framework, not authenticated by the adapter.
- Agent identity is deployment-fixed at guard-construction time (`config.agentId`), which is a materially stronger posture than a raw proposer-supplied `context.agent_id` on every call — but it is still not derived from an authenticated principal via `createTrustedExecutionContext`.
- `tool` and `depth` fields are **not** populated by any current adapter's default normalization. Because of this, `ToolAmplificationModule` and `RecursionDepthModule` do not constrain execution on adapter-routed paths where those fields are absent — a per-tool cap or a recursion-depth limit configured in policy state simply has no `intent.tool`/`intent.depth` value to match against for these adapters.
- Adapters remain, deliberately, **lower-level guard integrations**. They do not fabricate a `TrustedExecutionContext` on the caller's behalf, because — per `packages/langgraph/README.md` — "a framework adapter has no authenticated principal of its own, so it cannot construct that context honestly."

Deployments that require authenticated Tier 1 evaluator-input provenance must establish trusted execution context at an authenticating PEP layer of their own and integrate `createSecureGuard` there; the shipped adapters do not provide this today, and migrating them is explicitly deferred (see `openzeppelin-scope-v2.md` §3, "Adapters are not presumed to establish authenticated Tier 1 provenance").

## 8. Residual: signed does not mean authoritative

Stated normatively in `docs/security/SECURITY.md §7`, and repeated here because it governs every other residual in this document:

A valid Ed25519 signature over an `AuthorizationV1`, `DelegationV1`, or envelope artifact proves:

- **Integrity** — the artifact has not been altered since signing.
- **Authenticity relative to `trustedKeySets`** — the signer controls a key the verifier has explicitly chosen to trust.

It does **not** prove:

- **Semantic truth** — that the policy or state used to produce the decision was itself correct or legitimate.
- **Authorization authority by itself** — `policyId` is a content hash of policy configuration, not a capability granted by a trusted root; a matching `policyId` is not evidence of issuer legitimacy.
- **Currentness** — a validly-signed artifact does not prove the state it was computed against is still the current state (see §4).
- **State freshness** — signature validity and state freshness are orthogonal; an authorization can be perfectly valid and signed against state that has since changed.

## 9. Residual: enforcement placement

OxDeAI cannot prevent a deployment from exposing an alternate, unguarded execution path to the same underlying action. The library enforces the boundary for every call that is actually routed through it; it has no visibility into, and no ability to block, a code path that reaches the same side effect without calling `OxDeAIGuard`/`createSecureGuard` at all.

**Non-bypassability is guaranteed only for execution paths actually routed through the reviewed enforcement boundary.** `examples/non-bypassable-demo` demonstrates one concrete architecture that achieves this in practice (a shared-secret bearer token gating the protected upstream HTTP endpoint, verified independently of the guard's own decision), but this is a demonstrated deployment pattern, not a protocol-enforced universal property. A deployment that leaves a second, ungated route to the same resource has not been protected by OxDeAI regardless of how correctly the guarded route is configured.

## 10. Deferred capabilities

The following are open or planned areas, per `ROADMAP.md` and the referenced issues. None of them are implemented, and none should be described as implemented in any 2.0 release material:

- **`ExecutionReceiptV1`** — planned in `ROADMAP.md` v4.x ("Verifiable Execution Evidence"); no implementation exists. [#249](https://github.com/oxdeai/oxdeai/issues/249) is a compatibility-decision-only issue (RATS/EAT/COSE) that explicitly gates this future artifact and explicitly makes no protocol change itself.
- **Human-approval / STEP_UP semantics** — see §6.
- **Tier 2 provenance/state** — an authoritative `StateProvider`/`PolicyProvider` abstraction beyond the current `getState`/`setState` CAS contract, described as future work in `docs/architecture/decisions/tier1-evaluator-input-provenance.md` ("Authoritative State" section) but not implemented.
- **Tool default-deny axis** — [#214](https://github.com/oxdeai/oxdeai/issues/214), open. `state.allowlists` currently has no tool axis; a tool absent from `tool_limits` configuration is permitted by default rather than denied.
- **Instruction/proposal provenance** — [#251](https://github.com/oxdeai/oxdeai/issues/251), open, decision-record-only. OxDeAI authorizes an already-formed intent; it does not attempt to establish the causal chain (system prompts, skills, MCP manifests, etc.) that produced the proposal.
- **Future adapters** — any adapter not present in the repository as of the reviewed commit.
- **Related policy-expressiveness gaps**, all open, all P2: [#216](https://github.com/oxdeai/oxdeai/issues/216) (no credential provenance/scope binding), [#217](https://github.com/oxdeai/oxdeai/issues/217) (argument provenance not expressible beyond an opaque `metadata_hash`), [#218](https://github.com/oxdeai/oxdeai/issues/218) (no approval-state workflow concept — related to §6), [#219](https://github.com/oxdeai/oxdeai/issues/219) (per-tenant limits are a naming convention, not a verified property).

## 11. Release claim boundary

| Area | 2.0 status | Safe claim | Claim to avoid |
|---|---|---|---|
| Pre-execution authorization | Implemented, tested | "Execution requires a prior ALLOW decision from the PolicyEngine, evaluated against explicit `(intent, state, policy, evaluationTime)`." | "OxDeAI authorizes every agent action" (implies coverage of paths not routed through the guard) |
| Cryptographic verification | Implemented, tested, conformance-covered (Go/Python for canonicalization, signed-KRL, Profile C portable subset; TypeScript for the full protocol suite) | "Authorization artifacts are Ed25519-signed and independently, offline-verifiable." | "Any conformant implementation can verify any artifact" (only the TypeScript reference implementation performs full verification today) |
| Replay/freshness | Implemented, tested | "Authorization IDs are single-use via a pluggable `ReplayStore`; trusted-evaluation-time freshness bounds reject stale or future-dated intents." | Any claim that the default in-memory `ReplayStore` is production-durable — it is explicitly documented as development-only in `packages/guard/README.md` |
| Trusted context | Implemented, tested, not yet adopted by any shipped adapter | "`createSecureGuard` rejects a proposer claim that conflicts with a trusted premise for `agent_id`, `depth`, and `tool` (when a trusted route premise for `tool` exists)." | "Trusted execution context is established for every integration" (only true for deployments that call `createSecureGuard` directly) |
| Evaluator provenance | Partially implemented (see §3) | "Self-declared identity, depth, and route-derived tool claims cannot silently override a trusted premise." | "Complete Tier 1 evaluator provenance" or "state is authoritative" |
| External TOCTOU | Not implemented for external resources (see §4) | "OxDeAI's policy-state CAS detects concurrent policy-state mutation." | "OxDeAI is TOCTOU-safe" without the "for its own policy state, not external resources" qualifier |
| Post-execution audit | Partially implemented (see §5) | "Every decision up to and including a successful ALLOW is recorded on `onDecision` or `onBoundaryEvent`." | "Every failure is captured in the audit stream," including failures after `execute()` has started |
| Adapters | Implemented, none using `createSecureGuard` (see §7) | "All five adapters delegate authorization to `@oxdeai/guard` and are exercised in CI." | "Adapters provide authenticated Tier 1 provenance" |
| Human approval | Not implemented (see §6) | *(no current claim to make)* | Any claim referencing STEP_UP or human-approval binding as a 2.0 capability |
| AARM | Not claimed, no formal mapping established for AARM Core specifically | "OxDeAI's design maps to the independently-published ETA framework invariants" (per `docs/standardization/execution-time-authorization-alignment.md`) | Any claim of AARM Core conformance |

## 12. Relationship to external review

This document is expected to change as a result of the OpenZeppelin review described in `docs/audits/openzeppelin-scope-v2.md`:

- Reviewer findings may surface **new** residuals not listed here; this document must be updated to include them.
- This document must be re-reviewed and updated after the `S_freeze` review completes, and again after `S_fix` is produced.
- Any finding the project accepts without remediating (rather than fixing) must be reflected here as a residual before any 2.0 artifact is published, with the same treatment given to the residuals already listed in §3–§9.
- Final published claims for the 2.0 release must match both the exact `S_fix` commit and the residual set as it stands after the review concludes — not the residual set as it stands in this pre-review draft.
